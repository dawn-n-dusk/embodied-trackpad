# Project instructions

- Read README.md, STATUS.md, docs/architecture.zh-CN.md, and the current bounded task before editing.
- Current hand target is ADR 0007: user-confirmed LEAP v1 Full, four fingers and 16 independent motor/joint channels, with XC330-M288-T motors. This supersedes ADR 0006's v2 target. Existing v2 17-motor/21-joint code and measured results remain immutable regression evidence, not v1 acceptance. Optional fingertip FSR is a proposed add-on, not installed hardware. New v1 work needs a separate embodiment/layout/calibration and the prepared v1 rebaseline task. Do not relabel Allegro/v2 results or assume G1/H2 plug-and-play support.
- The current learning recommendation is small-policy engineering baselines plus a pretrained pi0.5 full-finetuning/RTC candidate, followed by corrective data and independent evaluation. GR00T N1.7 is a later controlled comparison; LingBot-VLA 2.0 mechanisms are research references. These are proposals, not trained policies. Do not infer an Orin 100 Hz neural inference guarantee, installed FSRs, or unattended real-world RL authorization from the architecture discussion.
- The user confirmed RL as a conditional middle/later-stage route: omit it if agreed task performance is sufficient; otherwise use targeted RL to address remaining policy limitations after calibration, data and execution issues are diagnosed. Freeze a baseline, reward, evaluation, resource budget and recovery criteria before dispatch; this decision does not itself start a training run.
- ADR 0008 records the user's chosen full fine-tuning route on H800/other allocated compute; LoRA comparison is not a first-stage requirement. Prioritize simulation and initial model validation. Physical FSR and conductive fingertip recognition are deferred and do not gate simulation. Preserve missing sensor masks and distinguish device-internal contact truth from actor observations.
- The coordinator owns design, review, integration, GitHub publication, and milestone acceptance. Kimi implements within the task's explicit file and resource scope.
- User clarification on 2026-10-30: operational execution also belongs to Kimi. Delegate environment installation, VM lifecycle/configuration, server deployment, simulation/benchmark execution, training, capture/input experiments, and live streaming to bounded Kimi tasks. Codex defines architecture, contracts, budgets and acceptance, reviews source/evidence and live views read-only, maintains docs, and integrates/publishes Git changes. Do not silently take over worker implementation or deployment when a call times out; recover the checkpoint and re-scope the Kimi task.
- Use a clean dedicated branch, normally `codex/<topic>`. Workers do not commit, push, merge, or change repository settings unless explicitly included in their task.
- Treat STATUS.md as the current evidence boundary. Proposed, implemented, locally tested, GPU tested, real-Mac tested, trained, and physically validated are different states.
- Each meaningful step must have an append-only experiments/ledger.jsonl entry or a draft experiment record pending coordinator integration. Record UTC timestamps, source revision, seed/config, commands/checks, observed outcome, artifact checksums, and remaining limitations. Never fabricate metrics or backdate execution.
- Update relevant docs and CHANGELOG.md with behavior changes. Keep superseded designs as history. Corrections supersede prior records rather than silently rewriting outcomes.
- Preserve the action path: motor output -> actuator/controller -> physics -> touch device -> GUI. Actor code must not bypass the robot with click coordinates or consume oracle GUI/cursor state. Privileged teacher/evaluator fields are separate.
- Never connect to real robot serial/camera/control services. Mac input injection is outside the foundation package; future bridge work requires an explicit task scope and a dedicated test account/environment.
- The user authorized the current M5 as the test host on 2026-10-30 because the M1 is unavailable. Initial Mac work uses this project's confined native app; no global host input/capture. A full macOS guest is a separate acceptance stage. Record App Sandbox entitlements and measured restrictions separately.
- Account names, SSH aliases, remote paths, credentials, private screenshots, raw sessions, downloaded weights, and full third-party papers do not enter the public repository. Use environment variables or ignored local configuration.
- GPU jobs require explicit allocation and bounded resources. Do not infer that an idle GPU is reserved. No long training without a task specifying budget, configuration, checkpointing, and stopping criteria.
- Tests should check meaningful boundaries and behaviors. Report actual commands, failures, and untested paths. Do not equate schema or unit-test success with physical or task success.
- Keep all third-party attribution and license requirements. Pin upstream asset/model revisions and record checksums; model availability is not permission to redistribute all associated data.
