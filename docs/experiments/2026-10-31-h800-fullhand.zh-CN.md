## 原因与修正

MuJoCo Warp 3.17 的 `get_data_into` 回读写入 `contact.geom[:]`。先前分类器读取的旧 `geom1/geom2` 字段在该路径中未正确更新，导致实际指尖与板面的接触被归入其他类别。

Kimi 改为读取 `contact.geom[0:2]`，并增加 GPU 原生接触数组的独立诊断通道。在实际按压阶段第 720 步，四个批量规模均观察到：

| 字段 | 实际结果 |
|---|---|
| 原生 GPU 接触几何编号 | `[80, 101]`：中指尖与触控板面 |
| 回读 `contact.geom` | `[80, 101]` |
| 两路有符号接触距离 | `-0.000026436522603034973 m` |
| 旧 `geom1/geom2` | 随批量出现 `[0,0]` 或无效大整数，不能用于分类 |

模型 XML、场景适配器、重置状态和 1800 行控制序列的哈希与失败作业一致。没有更换物理参数、轨迹或放宽容差以取得通过。

## 通过了什么

43 项包括 7 项 CPU/控制序列检查、各批量 GPU 状态与接触检查，以及设备名称核验：

- CPU 逐步检查通过；完整重放的最终位置、最大穿透与冻结轨迹相符。
- GPU 采样中观察到指尖接触；按压结束后最终抬指状态，两路均为零接触。
- 采样最大穿透约 **0.669 mm**，低于预设 1 mm 界限；采样中未观察到其他类别碰撞。
- 所有世界最终 `qpos/qvel` 为有限值；相同初态与控制下，批内最终状态差异为零。
- 世界 0 与 CPU 最终状态最大差约 `1.15e-6`（位置坐标）、`1.16e-5`（速度坐标），在原设容差内。
- 接触与约束容量采样值在分配范围内：512 世界时总接触数采样峰值 512/2048，单世界约束峰值 3/1024。

**覆盖范围必须与结果一起使用：** GPU 接触仅检查世界 0，每 60 步及最后一步采样；所有世界的位置也是每 60 步采样，速度只做了全世界最终有限性检查。没有逐步、全世界的接触/速度/加速度证明。容量采样通过也不证明瞬态从未溢出。GPU 求解器警告计数未知，不能写成零警告。

`gpu_contact_channels_agree` 比较的是采样中是否出现板面接触；它不是全轨迹每个接触对、数量和力的一致性证明。协调者另核对了第 720 步首个诊断接触的确切编号与距离。接触法向力尚未完成真实标定。

## 完整周期的吞吐

CPU 与 GPU 都从相同重置状态计时，施加同一套 1800 行控制序列。GPU 预热在隔离的临时世界执行，计时阶段重新重置；CPU 无额外预热。以下是本次运行的单次测量，未做重复统计：

| 后端 | 世界数 | 完整周期耗时 | 总世界步/秒 |
|---|---:|---:|---:|
| CPU MuJoCo | 1 | 0.03305 s | 54,464 |
| H800 / Warp | 1 | 13.627 s | 132 |
| H800 / Warp | 32 | 13.706 s | 4,202 |
| H800 / Warp | 128 | 13.792 s | 16,706 |
| H800 / Warp | 512 | 13.741 s | 67,070 |

512 世界时，总吞吐约为这次单 CPU 世界基线的 **1.23 倍**。单世界速度仍显著慢于 CPU；512 世界执行 3.6 秒模拟时间用了约 13.74 秒，不能把总吞吐解释为单机器人实时性能。

当前每一步仍在 Python/CPU 构造、复制控制数组并启动 GPU 计算，末尾显式同步；不能说它逐步显式同步，也不能假定没有其他内部开销。尚未采用 CUDA graph，没有多核 CPU 批量基线，没有 GUI、视觉推理或优化器开销。第一阶段首步约 0.897 秒时已有编译缓存，字段虽名为 `cold_first_step_s`，不能解释为冷编译时间。因此这次只建立特定实现的吞吐基线，不证明端到端训练有同等加速。
