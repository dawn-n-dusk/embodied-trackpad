## What the probe does

[tools/gpu_probe.py](../../tools/gpu_probe.py) runs inside the allocation and:

1. Records sanitized metadata: package versions, Python/OS, GPU name, driver
   and CUDA versions. Hostname, user and job id are stored only as truncated
   SHA-256 hashes; no absolute paths are recorded.
2. Builds a tiny contact scene: a capsule fingertip on an actuated slide joint
   (position actuator, kp=20) pressing a static box "trackpad", 240 Hz
   timestep, 480 steps.
3. Runs the CPU reference with `mujoco` and the GPU batch with `mujoco_warp`
   (`put_model` / `put_data` / `step`, state read back via `get_data_into`) at
   1 and 32 worlds. CUDA unavailability or any solver/buffer error fails the
   probe; there is no CPU-Warp fallback path.
4. Checks: finite qpos/qvel in all worlds, contact observed (ncon ≥ 1),
   fingertip rest height within 2 mm, CPU/GPU final state agreement within
   5 mm / 5 cm·s⁻¹.
5. Measures warmup (first `mjw.step`, includes one-time kernel compilation)
   separately from steady-state stepping on a fresh pre-compiled batch.

## Invocation (placeholders)

```bash
# once, on a login node: create the isolated environment
python3.10 -m venv .venv && . .venv/bin/activate
pip install -r env/probe-requirements.txt

# submit; account/partition are supplied at submit time, never stored in the repo
PROBE_VENV=<VENV_PATH> PROBE_WORKDIR=<WORKDIR> PROBE_SOURCE_COMMIT=<COMMIT> \
  sbatch --account=<ACCOUNT> --partition=<PARTITION> tools/gpu_probe.sbatch

# verify lifecycle afterwards
sacct -j <JOB_ID> --format=State,ExitCode,Elapsed,NodeList
```

[tools/gpu_probe.sbatch](../../tools/gpu_probe.sbatch) carries only the generic
bounds (`--gres=gpu:1 --cpus-per-task=4 --time=00:20:00`) and reads the venv /
workdir from `PROBE_*` environment variables.

## Results

| Check group | Outcome |
|---|---|
| CPU reference | finite states; 1 contact; fingertip rest z = −0.177 mm |
| GPU device | NVIDIA H800 via CUDA (no CPU fallback) |
| GPU correctness, nworld=1 | finite states; ncon=1; \|Δqpos\| = 4.2e-9 m, \|Δqvel\| = 1.6e-8 m/s vs CPU |
| GPU correctness, nworld=32 | finite states in all worlds; ncon=1 in world 0; identical agreement |

Performance (measured, this 1-DOF scene only — no extrapolation):

| Config | Warmup (first step) | Steady state |
|---|---|---|
| GPU, 1 world | 25.32 s (one-time Warp kernel compile) | 243 steps/s |
| GPU, 32 worlds | 0.005 s (compile cached) | 239 steps/s/world → 7654 world-steps/s |
| CPU, 1 world (reference) | — | 246053 steps/s |

At this tiny scale GPU stepping is slower than the single-world CPU reference,
including the total throughput of the tested 32-world batch. Increasing the
batch scales the GPU's aggregate throughput; **no GPU-over-CPU crossover was
measured**. This matches the architecture doc's warning that small-batch MJWarp
is not guaranteed to beat CPU. This ungraphed stepping loop is an environment
probe, not an optimized full-hand throughput benchmark.

## Failure history within this probe

The first submission failed in 4 s: the script called `warp.get_device(int)`,
which warp-lang 1.18.0 rejects (`Invalid device identifier: 0`). Fixed to
`get_cuda_device(0)` plus an explicit `ScopedDevice("cuda:0")`; CPU-only smoke
test re-passed; the second submission completed. This was a probe-script bug,
not a scheduler/driver/solver failure; the failed job's allocation was released
automatically on exit.

## Limitations

- Tiny deterministic settle scene; CPU/GPU agreement at ~4e-9 m does not
  preset tolerances for richer scenes.
- One-time Warp kernel compilation (25.3 s, cached in the cluster home) must be
  budgeted into any short GPU job.
- No rendering, no hand embodiment, no GUI, no policy; throughput numbers make
  no full-hand or large-batch claim.
- Contact buffer sizing used `put_data` defaults (`naconmax` 48/1536); overflow
  behavior for dense multi-contact scenes is untested.
