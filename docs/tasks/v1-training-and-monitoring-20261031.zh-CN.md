# LEAP v1：按既定训练顺序推进实时监看

2026-10-31。用户要求将短时关节演示升级为训练过程中的实时监看，并明确 8192 环境不是当前目标。以下是本轮冻结的执行顺序和预算；派发、通过、训练开始分别记录。

## 当前事实

v1 Full 手部 CPU 基线和本地实时画面已验收；v1 板面接触、视觉反馈、项目训练数据、策略训练尚未验收。旧 v2 在 H800 的最高实测是 512 个相同脚本环境，不能外推为 v1 的 8192 个训练环境。全量微调路线保持 ADR 0008，不改变为 LoRA，也不提前启用真机 RL。

## 第一批工作

两项工作可由 Kimi 在独立工作树并行完成，协调者负责审查、集成和公开记录。

1. **v1 板面接触前置验证。** 在现有完整 16 通道模型上加入固定触控板，验证清空、落指、滑动、抬指。所有执行仍是 `ctrl → mj_step → 真实求解接触 → touch.v1`。先完成单指可复核周期，再接原生受限 GUI 的连续反馈。仅 CPU、两数值线程、物理计算累计最多 300 秒、产物最多 250 MiB、Kimi 调用最多 900 秒。不启动训练、不收集 D1、不控制系统桌面。
2. **本人账户的训练运行时。** 安装本人目录中的独立 GPU Python 环境，验证 PyTorch、CUDA 和 MuJoCo Warp。下载预算 12 GiB、环境与缓存合计最多 20 GiB；仅一个 H800 作业、最长 20 分钟，只做 1/32 世界短探针与 CPU/GPU对照，不跑 8192、不下载大模型权重、不启动全量微调。GPU 型号、实际调度资源、显存、耗时、失败和作业退出必须记录。不得复用旧借用账户的运行时。

接触验证通过后，再冻结 v1 在线反馈合同。只有画面确实改变后续动作，才进入 D1 数据试采与质量检查。最初 200–500 条轨迹是采集规模的规划，不是已有数据或当前运行授权。小模型工程基线用于验证观测、动作块与执行管线；π0.5 全量微调须独立冻结数据版本、预训练权重、训练配置、GPU 预算、检查点和评估集。

## 训练监看的接口与验收

- 训练器保留全部并行物理环境，但只导出少量观察环境的最新状态，首版一个环境。界面显示 `run_id`、环境编号、训练步数、策略/检查点版本、仿真时间、接收时间、帧号、损失/回报和当前阶段。未提供的指标显示缺失，不填造数值。
- 训练环境的实时状态与固定检查点的独立评估回合分别标记。观察端可以依据实际 GPU 状态做 CPU 渲染；这种只用于显示的状态同步不能回写训练环境，也不能宣称观察端正在独立执行策略。
- 先用 640×480、5–8 FPS；不渲染全部环境。测量开启/关闭观察后的采样吞吐与训练迭代耗时，发现明显拖慢再降低帧率。
- 生命周期随训练作业：等待环境/数据、训练、评估、停滞、失败、完成。视频新鲜度以实际收到并显示的新帧为准；作业或模型停止后不得继续显示实时训练状态。任务结束后最后一帧可留作历史画面，明确标为结束。
- 远程状态通过本人账户的受限传输进入本机，仅本机回环地址提供查看页面。日志保存必要的身份和源版本，公开记录移除账号、节点、私有路径与连接配置。
- 首次训练监看验收必须同时具有真实梯度更新、检查点变化、策略动作经物理执行、画面更新的证据。当前脚本演示不满足这一条件。

## 扩容规则

容量在训练流程正确之后测量。从 32/128/512 逐级扩大，按实际显存、接触容量、每秒有效样本、训练迭代时间和评估表现决定后续档位。8192 是候选规模；本轮没有分配其运行预算。环境数量、并行采样速度和最终任务学习质量分别报告。
