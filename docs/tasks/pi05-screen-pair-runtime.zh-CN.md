# 双屏幕输入的真实 OpenPI CPU 验证

2026-11-02 HKT。显式全屏和原像素局部图的适配已通过软件检查；本任务验证固定官方运行时实际保留两路图像。Kimi 准备并运行诊断，协调者审查源码、绑定许可、独立核对数组与调度终态。

## 输入与验收

- 使用已审核的两张真实屏幕图、16 关节状态和 25×16 动作标签。固定源数据、tokenizer、OpenPI 与依赖版本；私有图像和运行路径不公开。
- 对比原 Observation 构建器，核对全图、状态、token、动作和有效 16 维 mask 完全保留。
- 全图与 `screen_local_0_rgb` 必须在实际官方预处理前后保持正确键、顺序、形状、类型和像素。根据当前 RGB 和记录的裁剪原点独立重建局部图，核对边缘填充与缩放；不得以调用同一构建函数两次代替独立像素比较。
- 缺失腕部传感器仍为 false 的来源记录。局部图逐像素 padding mask 不冒充模型注意力 mask。
- 全黑合成图仅作为无效局部图的负控，不进入训练数据；验证局部 mask 为 false、缩放后像素为 -1。缺失、额外、顺序错误的图像字段必须拒绝。
- 记录现有默认三相机预处理不能直接消费新布局的事实；此任务不创建模型或验证损失、动作采样器。

## 单次资源合同

准备源码、独立审查后再签发一次有效的文件散列绑定许可。唯一 CPU 作业：请求 2 CPU、最多 4 个可见逻辑 CPU、16 GiB 内存、2 个数值线程、180 秒 Slurm 时限、150 秒内部时限加最多 10 秒清理；新产物最多 16 MiB。仅使用现有运行时，不安装依赖、下载权重或在登录节点进行模型计算。

0 GPU、0 模型前后向、0 优化器更新。提交前核对已有回执、进程身份与本项目队列；不重复提交、不自动重试。失败保留报告、数组、源码和用量，先定位原因。首轮 GPU smoke 用量不变。

## 后续边界

通过仅建立真实输入变换一致性，不证明模型已使用局部视图或控制精度提升。随后单独实现 JAX 编译安全的训练损失和推理采样器路由，保留原三相机调用作为回归路径；正式动作时间尺度仍需数据拼接与执行语义验收。

## 实际验收

单次 CPU 作业在 31 秒完成，2 CPU、0 GPU、峰值 RSS 935.45 MiB。121 项实际运行检查通过；协调者另外完成 99 项独立检查，核对 36 个数组的散列、像素、状态、token 和动作。两张真实图各自的 116 个光标像素均完整保留，独立重建的局部图像素误差为 0。全黑负控和缺失/额外/顺序错误字段按预期处理。[实际记录](../../experiments/records/pi05-screen-pair-runtime-accepted-20261102.json)。

原三相机预处理拒绝新字段布局的结果也已实际观察到。当前许可已消耗，资源释放；不重复同一作业。这是输入处理验收，尚未验证双视图对模型动作的影响。准备阶段的两次 Kimi 超时、脚本缺陷和修正均保留记录。
